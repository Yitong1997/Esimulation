# Zemax POP Benchmark Design

Date: 2026-06-14

## Context

The current biconic POP validation script compares the local POP API against Zemax data saved manually from OpticStudio. This is useful for debugging, but it is not a reliable benchmark workflow because the Zemax reference data is not generated by the script and can drift from the tested `.zmx`, sampling, beam settings, or output surfaces.

The goal is to build a reproducible benchmark between the local POP API and Zemax Physical Optics Propagation through ZOSAPI. The benchmark must support two Zemax POP input modes:

1. Direct Gaussian beam propagation through Zemax `GaussianWaist`.
2. Non-ideal input field propagation through Zemax `File` beam mode using ZBF.

The second mode is the higher-value case: the same non-ideal ZBF input should be propagated by Zemax and by the local POP API, then compared as complex fields at selected surfaces.

## Decisions

- Use a manual benchmark runner plus optional pytest benchmark tests.
- Use per-surface ZBF complex-field comparison as the primary pass criterion.
- Add a source/io layer ZBF input adapter for the local POP API.
- Do not modify the core POP propagation algorithm.

The existing `CustomSource` path already allows the local POP API to accept a custom amplitude and phase field. The missing piece is a formal ZBF adapter that preserves Zemax ZBF semantics instead of treating `Ex` as an ordinary physical phase grid without checking the pilot/reference metadata.

## Goals

1. Generate Zemax POP reference output directly through ZOSAPI.
2. Compare Zemax and local POP API outputs without relying on manually exported files.
3. Support both ideal Gaussian input and non-ideal ZBF input.
4. Keep benchmark logic outside the core propagation implementation.
5. Make failures diagnosable through JSON summaries, per-surface NPZ files, and optional plots.
6. Provide a pytest entry point that can be enabled explicitly on machines with Zemax installed.

## Non-Goals

- Do not rewrite `propagate()` or the element/free-space propagation algorithms.
- Do not add polarization propagation support in the first version.
- Do not support arbitrary mid-system ZBF injection in the first version.
- Do not make Zemax-dependent tests run by default in normal pytest.
- Do not depend on `D:\BTS_ZosApi` at runtime except as a reference for implementation patterns.

## Architecture

Add a benchmark layer around the existing POP API:

- `sandbox/zemax_pop_benchmark/`
  - manual runner scripts and benchmark configs;
  - ZOSAPI runner;
  - report generation and output organization.
- `tests/benchmark/`
  - pytest entry points that call the same benchmark code;
  - skipped by default unless an environment variable enables Zemax tests.
- `pop/io/zbf.py`
  - package-local ZBF reader/writer or wrapper around existing ZBF logic;
  - reference phase calculation matching Zemax header semantics.
- `pop/source.py`
  - `ZbfSource` or `CustomSource.from_zbf()` as a thin source adapter.

Core propagation remains unchanged. The adapter only needs to implement the existing source contract:

```python
amplitude, phase, pilot_beam, proper_wfo = source.create_initial_wavefront()
```

## ZOSAPI Runner

`ZosPopRunner` is responsible for all Zemax work:

1. Connect to OpticStudio through ZOSAPI/ZOSPy.
2. Load the target `.zmx`.
3. Configure `PhysicalOpticsPropagation`.
4. Run POP for irradiance/phase diagnostics when needed.
5. Save output ZBF files through `SaveOutputBeam`.
6. For per-surface comparison, use `SaveBeamAtAllSurfaces` when available, or run multiple start/end surface jobs if all-surface output is not sufficient.

The runner should expose two public methods:

- `run_gaussian_direct(config) -> ZemaxPopRun`
- `run_zbf_input(config, input_zbf) -> ZemaxPopRun`

The implementation should follow the existing `D:\BTS_ZosApi\ao_core.py` pattern:

- Gaussian mode uses `beam_type="GaussianWaist"` plus beam parameters.
- ZBF mode uses `beam_type="File"` and `beam_file="<name>.ZBF"`.
- Output ZBF stems should not include `.ZBF` when passed as `output_beam_file`.

## POP API Runner

`PopApiRunner` is responsible for local propagation:

1. Load the same `.zmx` through `pop.load_zmx`.
2. Build the source:
   - Gaussian case: `GaussianSource`.
   - ZBF case: `ZbfSource` or `CustomSource.from_zbf()`.
3. Call existing `propagate()`.
4. Return the full `PropagationResult` for per-surface comparison.

This runner must not special-case propagation internals. It only translates benchmark config into public POP API calls.

## ZBF Source Adapter

ZBF contains both complex field samples and pilot/reference metadata. Zemax stores `Ex`/`Ey` as complex amplitudes relative to the ZBF header reference beam. A naive conversion of `angle(Ex)` to physical phase is therefore ambiguous.

The adapter should make the conversion explicit:

- Read `nx`, `ny`, `dx`, `dy`, `wavelength`, `index`, `zx`, `zy`, `Rx`, `Ry`, `wx`, `wy`, `Ex`, and optionally `Ey`.
- Reject unsupported polarized inputs initially unless the caller chooses an `Ex`-only mode.
- Compute the Zemax reference phase from the header.
- Build a local POP input field in a declared mode:
  - `reference_relative`: keep `Ex` as the residual field and construct matching pilot metadata.
  - `physical`: use `Ex * exp(i * zemax_reference_phase)` as the physical field.
- Default to `reference_relative` for benchmark parity with Zemax `File` beam mode.
- Create a PROPER wavefront using the same source interface as `GaussianSource` and `CustomSource`.

The source should preserve metadata in diagnostics:

- input ZBF path;
- input ZBF units and sampling;
- reference mode;
- pilot parameters derived from the ZBF header;
- any unsupported header conditions or approximations.

The first version may require circular/symmetric pilot metadata. If the ZBF has significantly different X/Y pilot parameters, the adapter should fail clearly or mark the run as unsupported rather than silently collapsing astigmatic metadata into a radial pilot.

## Benchmark Cases

### 1. Gaussian Direct

Purpose: sanity check that the local POP API and Zemax agree for the simplest comparable input.

Zemax:

- `PhysicalOpticsPropagation(beam_type="GaussianWaist")`
- Set waist X/Y, sampling, width, power mode, start/end surfaces.
- Save output ZBF at target surfaces.

Local POP:

- `GaussianSource(wavelength_um, w0_mm, z0_mm, grid_size, physical_size_mm)`
- Existing `propagate()`.

Comparison:

- Per selected surface, compare Zemax ZBF against the matching POP surface state.
- Use the reference-relative comparison logic already proven in the existing biconic script tests.

### 2. ZBF Input Non-Ideal

Purpose: benchmark propagation of a non-ideal input complex field.

Input:

- A ZBF containing the same non-ideal field for both systems.

Zemax:

- Copy input ZBF to the Zemax `POP/BEAMFILES` directory.
- Run `PhysicalOpticsPropagation(beam_type="File", beam_file=input_name)`.
- Save output ZBF at target surfaces.

Local POP:

- Read the same ZBF through `ZbfSource`.
- Propagate through the same `.zmx`.

Comparison:

- Use the same per-surface comparison pipeline as Gaussian direct.
- The benchmark summary must record input ZBF metadata and adapter mode.

## Comparison Metrics

The primary comparison is per-surface complex-field agreement under a common reference convention.

For each matched surface:

- grid shape;
- POP sampling and ZBF sampling;
- wavelength;
- mask pixel count;
- relative intensity RMS;
- relative intensity peak-to-valley;
- phase piston;
- phase RMS after piston removal;
- phase peak-to-valley after piston removal;
- warnings or skip reasons.

The mask should default to pixels where both normalized intensities exceed the configured threshold.

Initial default thresholds should be loose enough for debugging:

- intensity RMS threshold: configurable, initially report-only;
- phase RMS threshold: configurable, initially report-only;
- strict pass/fail can be enabled once baseline behavior is measured.

## Output Layout

Use one run directory per benchmark run:

```text
output/zemax_pop_benchmark/<run_id>/
  config.json
  summary.json
  gaussian_direct/
    zemax_zbf/
    comparisons/
  zbf_input_nonideal/
    input_zbf/
    zemax_zbf/
    comparisons/
```

Each comparison directory should contain:

- per-surface `.npz` arrays;
- per-surface plots when enabled;
- `summary.json`;
- `summary.csv`.

## Pytest Integration

Add pytest benchmark tests that call the same code as the manual runner.

Rules:

- Skip by default.
- Run only when `BTS_RUN_ZEMAX_BENCHMARK=1`.
- Skip with a clear message when Zemax/ZOSAPI cannot connect.
- Use small grids, such as 128 or 256, unless overridden.
- Store artifacts under a test output directory.

Suggested tests:

- `test_gaussian_direct_benchmark_smoke`
- `test_zbf_input_nonideal_benchmark_smoke`
- `test_zbf_source_roundtrip_metadata`
- `test_zbf_source_rejects_unsupported_astigmatic_header`

The first two are Zemax-dependent. The latter two can be ordinary local tests if they use synthetic ZBF files.

## Error Handling

The benchmark should fail early and clearly for:

- missing `.zmx`;
- missing Zemax installation or failed ZOSAPI connection;
- missing or unwritable Zemax `POP/BEAMFILES`;
- ZBF sampling or wavelength mismatch beyond configured tolerance;
- unsupported polarized ZBF input;
- unsupported astigmatic pilot metadata;
- missing target surface ZBF output;
- no valid comparison pixels after masking.

Every skipped surface should include a structured reason in `summary.json`.

## Implementation Order

1. Extract or reimplement package-local ZBF read/reference utilities.
2. Add local tests for ZBF read/reference phase and `ZbfSource` metadata behavior.
3. Add `ZbfSource` or `CustomSource.from_zbf()` without changing propagation internals.
4. Build `ZosPopRunner` for Gaussian direct mode.
5. Build `ZosPopRunner` for ZBF File mode.
6. Build shared comparison/report code.
7. Add manual runner for the biconic expand validation case.
8. Add opt-in pytest benchmark smoke tests.

## Open Questions

- Whether Zemax all-surface ZBF output names are stable enough for automatic matching, or whether the runner should execute one target surface at a time.
- Whether first-version ZBF input should require radial pilot metadata, or approximate X/Y astigmatic metadata into a single pilot with an explicit warning.
- Which surfaces should be default comparison targets for the biconic expand case.
- Which measured thresholds should become hard pass/fail gates after the first reproducible baseline run.
